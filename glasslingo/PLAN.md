# GlassLingo 下一阶段改进方案

日期：2026-11-10。基线：0.5.1。状态：已进入 0.6.0 实现；当前交付与验证范围见 IMPLEMENTATION.md，未验证项仍是验收目标。

## 1. 本轮交付与已确认选择

| 模式 | 用户操作 | 默认显示与行为 |
|---|---|---|
| 框选翻译 | 按快捷键，框一块文字 | 延续现有能力，统一接入新的处理流程 |
| 全屏翻译 | 一次快捷键截取当前目标显示器 | 按文字块在原文附近显示译文，可切换侧栏；默认单次翻译 |
| 区域持续翻译 | 框定区域，开始待机 | 默认每 500 ms 检查一次；变化后识别、翻译，原区域不变则复用结果 |

已确认：全屏译文优先原位置附近覆盖；持续模式低占用优先、通常每秒检查 2 次。

首版持续模式限一个监测区域。用户可暂停、重选、调整区域、隐藏译文与停止会话。全屏高频持续扫描不作为默认游戏用法。

### 1.1 显示方式独立于翻译模式

用户补充确认：保留现有翻译浮窗，增加可选择的“原位覆盖”，尤其用于游戏区域持续翻译。它们复用同一识别和翻译会话，不重复发起请求。各模式记住上次选择。

| 显示方式 | 显示内容 | 交互 |
|---|---|---|
| 翻译浮窗 | 延续原有原文、译文及信息面板能力 | 可拖动、复制、展开原文/诊断 |
| 原位覆盖 | **只显示译文**，覆盖在原文字块或选定字幕区 | 运行时点击穿透、不抢焦点；调整通过外部控制面板或快捷键进入编辑状态 |
| 侧栏 | 统一阅读译文，必要时查看原文 | 用于全屏内容过多、布局不可靠或用户主动选择 |

“原位覆盖”具体约定：

- 无窗口标题、原文、行数、语言名、引擎名、耗时、token、关闭提示或常驻工具条。
- 使用紧贴文字块的遮挡底板盖住原字，再排版译文；可调底板颜色/透明度、字号、文字颜色与描边。透明底板可能透出原文，想完全遮住时需使用不透明底板。
- 这轮采用局部遮挡，不做耗资源的背景修复或图像生成。
- 区域持续翻译可将整个已选字幕区作为排版容器；有可靠 OCR 坐标时再按文字块精细覆盖。视觉 API 缺少坐标时不伪造原字位置。
- 加载、错误、暂停等状态放到托盘/控制面板，不把提示写进游戏字幕。新文字确认替换时撤下过期译文，避免旧对白遮住新对白；新译文就绪后显示，可流式填入。
- 停止、隐藏或目标失效时移除遮挡，露出游戏原画面；原文消失后及时撤掉译文和底板。
- 捕获排除必须连底板一起排除，防止覆盖译文妨碍下一轮识别；不可可靠排除时暂停原位覆盖并说明原因，不悄悄循环翻译自己的字幕。

## 2. 先解决现有流程的限制

基于当前源码发现：

- `App.xaml.cs` 同时处理截图、OCR、语言判断、翻译和窗口更新；继续把监测循环塞进去会放大状态问题。
- 后台任务多用 `CancellationToken.None`，旧结果可能晚到；现有窗口关闭也没有统一停止任务。
- Paddle 默认参数初始化，没有针对游戏限制推理线程；识别前还通过 PNG 编码产生额外分配。
- 翻译使用 `stream=false`，等全文返回才显示。
- 覆层会调用 `SetForegroundWindow` 并注册裸 Esc 全局热键；持续游戏覆层不能沿用这个行为。
- 当前图片变化与文字变化没有区分；仅比较截图 hash 会被动态背景持续触发。
- 当前视觉 API OCR 结果没有真实文字坐标，不能当成可精确贴回原位的文字块。
- 当前小字重认可能带来第二次推理；自动模式也可能多语言重认，需要纳入总预算。

## 3. 建议架构

```text
托盘 / 快捷键 / 控制面板
            ↓
TranslationSession（单次 / 全屏 / 持续区域）
            ↓
CaptureService → ChangeDetector → OcrScheduler → TextStabilizer
                                                   ↓
                                           TranslationCache
                                                   ↓ 未命中
                                        StreamingTranslator
                                                   ↓
                               OverlayPresenter / SidePanel
```

主要职责：

| 组件 | 负责的事 |
|---|---|
| `TranslationSession` | 状态、目标窗口/显示器、区域、会话版本、取消、暂停与恢复 |
| `CaptureService` | 截取目标、DPI/多屏坐标转换、捕获失败恢复；输出可复用帧 |
| `ChangeDetector` | 缩小预览差异、区域变化与文本候选区域判断 |
| `OcrScheduler` | OCR 单任务调度、最新帧替换、语言和模型策略、耗时预算 |
| `TextStabilizer` | 逐字出现、闪烁和噪声去重；判断何时提交文本 |
| `TranslationCache` | 文字、目标语言、provider/model、提示词和技术文本选项共同构成缓存键 |
| `StreamingTranslator` | SSE 增量、超时、取消、有限重试与供应商能力回退 |
| `OverlayPresenter` | 浮窗/仅译文原位覆盖/侧栏切换、文字块定位、流式更新、点击穿透、截图排除 |

Paddle 建议在单独的按需启动 worker 进程中运行：便于限制线程、隔离原生崩溃，并在不用时真正释放模型内存。Windows OCR 保持轻量进程内实现。OCR 接口明确声明是否自动多语种、是否有坐标、是否支持取消，避免现有路径重复推理。

## 4. 区域持续翻译：工作规则

### 4.1 检测与文字稳定

1. 记录目标区域的物理坐标及目标窗口关系；窗口移动、缩放、显示器变化时重新映射或暂停提示重选。
2. 默认每 500 ms 检查区域预览。没有变化就不运行 OCR、不发请求。
3. 检测到变化后做有限的稳定判断；短暂逐字出现可延迟 150–250 ms。必要时追加一次确认采样，避免每帧推理。
4. 图片变化不等于文字变化。动态游戏背景需要文字/边缘区域掩码与 OCR 文本去重共同过滤；不能承诺单个截图 hash 就能解决。
5. 比较规范化文字、文字块位置与行结构；不删除会影响语义的标点、数字和代码字符。新对白或新数字保留。
6. 只有确定的文字变化才提交翻译；相同内容命中缓存直接显示。

### 4.2 工作量始终有界

- 每个会话最多一个 OCR 任务；待处理帧只留最新一张，不排长队。
- 原生 OCR 无法立即取消时，等待当前调用完成，按版本丢弃过期结果；不再启动另一组线程。
- 默认一个翻译请求进行中，最多保留一份最新待译文字。原始画面每次变化不直接取消翻译，避免一直有请求却始终没有结果。
- 真实文本换代时取消或淘汰旧译文；旧 stream 的后续字符不能写入新对白。
- 取消本地 HTTP 等待不等于供应商一定停止计费；通过去重、限频和合并减少请求。
- API OCR 单独限制上传频率和请求并发；不能默认每秒上传两张全区域截图。
- 缓存有容量上限；第一阶段用内存 LRU，稳定后再决定是否增加持久化。

### 4.3 运行状态

待机 → 发现变化 → 识别中 → 翻译中 → 继续待机。额外状态包含暂停、等待模型、网络异常、目标失效。

浮窗可以保留上一条完整译文直到新内容可读；原位覆盖在确认新对白后撤下过期译文与遮挡，避免盖错内容。新字幕流式更新时保持稳定的排版容器。连续异常退避，避免刷弹窗。长时间 OCR 为空时清除过期字幕，不能无限显示旧对白。

## 5. 全屏翻译

- 默认截取鼠标所在/用户指定的一块显示器，避免把所有屏幕拼成巨大图片。
- 全屏截图保持文字可识别尺寸；超出 OCR 尺寸限制时分块并做重叠去重，不直接缩成模糊小图。
- OCR 保留文字块与原图坐标，按行距、列和阅读顺序分组，译文使用应用保存的坐标映射；不让翻译模型猜坐标。
- 译文在对应文字块附近排布，处理长译文扩展、重叠与屏幕边缘；无法安全排下的内容进入侧栏。
- 局部面板使用高对比度背景，可调整透明度；不对整个屏幕施加长期磨砂效果。
- 视觉 API OCR 无布局结果时先提供侧栏；获得并验证结构化文字块后再启用原位显示。
- 一次全屏翻译后不继续 OCR；再次触发才更新。持续模式优先框选字幕/对话区。

## 6. 流式翻译

- 为 `ITranslator` 增加增量输出契约，非流式供应商通过适配返回最终结果。
- OpenAI 兼容接口采用 `stream=true`、`ResponseHeadersRead` 与 SSE 解析；处理跨行/跨缓冲 UTF-8、`[DONE]`、断线、空回复、错误响应及可选 usage。
- 按 50–100 ms 合并 UI 更新，最多约 10–20 次/秒；不为每个 token 重新测量窗口和更新全部文字块。
- 区域字幕用普通文本流。全屏多块翻译按块 ID 关联，完整块逐块落位；解析失败能回退侧栏，不让译文贴错位置。
- 暂停/关闭停止新工作，并使所有旧结果失效；半截译文不作为完整缓存条目。
- 流式只改善首字和阅读等待。OCR 吞吐不足、API 排队或对白变化过快仍靠限频和最新任务策略处理。

## 7. 游戏轻量策略与捕获选型

### 7.1 默认游戏配置

| 项目 | 方案起点，需实测调整 |
|---|---|
| 检测采样 | 2 次/秒；允许用户切换省电/均衡/快速 |
| 本地 OCR | 一个任务；Paddle 先限制到 1–2 个推理线程，核查数学库实际线程数 |
| GPU | 本地 OCR 默认 CPU，减少与游戏争显存/计算资源；GPU 推理作为后续可选项评估 |
| 后台调度 | 后台 worker 低于普通优先级；不提高到高优先级或实时优先级 |
| 图像内存 | 只读回目标区域，复用缓冲，及时释放 Bitmap/帧/响应；避免 PNG 往返与整屏反复拷贝 |
| 文字处理 | 无变化不 OCR，同文不翻译，超预算主动降频 |
| 模型生命周期 | 按需加载；停止后可延时结束 worker 释放内存；暖待机与冷启动延迟可选择 |
| 界面 | 游戏覆层不抢焦点、不接管鼠标，静止时无持续装饰动画 |

### 7.2 捕获后端先比较再选择

保留现有 GDI 区域截图作为 2 Hz 小区域场景基线，验证 Windows.Graphics.Capture 在游戏窗口、裁剪读回和设备变化下的成本。不能因为 API 使用 GPU 就推断一定更轻；高刷新率游戏的逐帧回调与全屏读回也有成本。

只有需要时再引入 DXGI Desktop Duplication 备选；利用脏区域信息减少无效处理，同时处理设备丢失、切屏、分辨率和显示器变化。

持续捕获必须排除自己的译文与控制条，防止“识别译文再翻译”的循环。优先使用受支持捕获 API 的窗口排除能力，失败时将字幕移到检测区外，不使用频繁隐藏/显示产生闪烁。

### 7.3 游戏兼容范围

- 首批验收重点为窗口模式与无边框全屏。
- 独占全屏、受保护画面、HDR 与反作弊环境分别验证；不承诺所有游戏都能捕获和覆盖。
- 捕获和覆盖是两个不同能力：能截图不代表普通 WPF 覆层一定能显示在该游戏之上。
- 采用进程外桌面覆盖，不向游戏注入 DLL。黑屏/无法覆盖时给出可执行提示或侧栏显示。
- 游戏模式取消裸 Esc 全局拦截。Esc 仅在软件自己的设置/框选界面处理；隐藏、暂停与结束监测使用可配置专用快捷键并检查冲突。

## 8. GUI 与交互设计计划

采用 `impeccable` 的 Operate 模式：以任务清楚、状态可信、操作顺畅为设计标准。本节是待确认方向，不作为已完成的视觉稿或 DESIGN.md。

### 8.1 三个主要界面

1. **控制面板**：清晰的“框选翻译 / 全屏翻译 / 持续区域”入口；常用的语言、OCR、性能预设在同一层。持续区域有明确开始/暂停按钮和状态，不靠托盘气泡猜测是否运行。
2. **设置窗口**：分为“翻译、文字识别、游戏与性能、显示、快捷键”。API 字段随引擎展开；状态就近显示。固定底部保存操作，避免目前长表单需要大量滚动。
3. **游戏原位覆盖**：仅显示译文与必要的遮挡底板；运行中点击穿透。调整工具在独立面板或显式编辑状态提供。原文和诊断信息在浮窗/控制面板查看。

### 8.2 拟定视觉方向

- 用户补充确认：Glass 名字贴合毛玻璃、液态玻璃风格高光与通透层次，浮窗透明效果可调。采用 Windows 原生 Acrylic、半透明蓝灰底、柔白正文和低饱和蓝色强调；不支持时回退实色。
- 系统 UI 字体优先（Segoe UI / 中文回退微软雅黑），统一字号层次、图标笔触、间距和焦点状态。
- 细腻边缘高光、克制圆角与系统阴影；主面板和浮窗浓度分别可调，游戏字幕使用轻量透明底板，不叠加全屏模糊或持续折射动画。
- 动效服务于展开、状态切换和反馈，约 120–180 ms；尊重减少动态效果设置。持续模式不做呼吸光、持续模糊或整页入场动画。
- 长译文、中文/日文、DPI 100/150/200%、小屏、键盘导航都列入布局验收。

实现前先给控制面板、引擎设置、游戏覆层三张界面方案；确认后再写视觉 token 与组件规范。保留 WPF，使用主题资源与 ViewModel 组织界面状态。

## 9. 性能与正确性验收

下列是目标，不是已测成绩。先记录当前机器基线，再根据实际游戏测量调整预算。

| 场景 | 验收目标 |
|---|---|
| 暂停监测 | 无截图、OCR 或翻译请求；稳定后后台 CPU 目标低于 0.5% |
| 静止文字 60 秒 | 首次处理后相同文字不再发翻译请求 |
| 游戏区动态背景、文字不变 | OCR 有频率上限；翻译请求仍不重复；验证动画不会不断刷请求 |
| 典型字幕区域约 1024×300、模型已热 | 以 p95 本地变化处理/OCR 约 350 ms 为优化起点；记录不同后端与线程设置 |
| 流式响应 | 记录从采样、文字稳定、OCR 完成、发请求到首字/全文的各段耗时，不把网络延迟归入 OCR |
| 文字快速变化 | 内存与请求队列不持续增长，过期译文不覆盖最新对白 |
| 游戏影响 | 同场景对比平均 FPS、1% low、帧时间；目标平均 FPS 降低≤2%、1% low 降低≤5%，未达标则降频/缩区域再测 |
| 内存 | 分别报告主进程、Paddle worker、私有内存、工作集与峰值；不以安装包大小推断占用 |
| 停止/切屏/异常 | 停止后不再刷新，设备失效可恢复，无重复窗口与残留热键 |
| 显示方式切换 | 保留现有浮窗；切换原位覆盖不重复 OCR/翻译请求，不混入原文或诊断信息 |
| 原位覆盖 | 覆盖位置正确、不抢焦点、不挡鼠标；对白消失/停止后无残留底板，自身译文不进入下一轮 OCR |
| 长时运行 | 至少 30 分钟持续模式，无持续内存增长与请求堆积 |

Windows、Paddle、视觉 API 分别测试；至少中英日三种文本、逐字字幕、动态背景、不同 DPI。API OCR/翻译测试使用无敏感测试内容，并记录费用/请求数。

## 10. 实施顺序与交付门槛

| 阶段 | 工作 | 完成后可审查结果 |
|---|---|---|
| P0：基线与交互稿 | 测资源占用；比对区域捕获；Paddle 线程与模型档位；三张界面方案 | 一份性能基线 + GUI 方案，确定能达到的预算 |
| P1：会话与调度底座 | 拆分 App 主流程；取消/版本/有界队列；焦点/热键与截图排除 | 原有框选不回退，关闭后旧任务不会更新 |
| P2：全屏单次翻译 | 单屏截取、分块、文字布局、批量翻译；保留浮窗，新增仅译文原位覆盖与侧栏回退 | 全屏能翻，译文定位无明显重叠和错配；三种显示方式可切换 |
| P3：区域持续翻译 | 2 Hz、变化/文字去重、稳定、缓存、暂停恢复与目标绑定 | 字幕变化能更新，游戏后台工作量有界 |
| P4：流式与低占用调优 | SSE、增量 UI、worker 生命周期、自适应降频 | 首段译文更早出现，长时间运行与游戏性能达标 |
| P5：GUI 实现与发布 | 按已确认稿实现、DPI/键盘/异常状态、可重复打包与运行验收 | 可试用版本、性能报告、完整依赖和清晰版本号 |

GUI 的结构设计在 P0 开始，P5 做整合验收；功能开发期间不继续堆叠当前长表单。

分发提供完整离线包；另评估“Windows/API 主包 + 可选 Paddle 组件包”。Paddle 延迟加载与可选组件解决的是不同问题：前者影响运行内存/启动，后者影响磁盘与下载量。

## 11. 参考依据
